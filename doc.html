1 System Architecture Blueprint
HIGH-LEVEL OVERVIEW

CrowdSourced is an enterprise civic technology portal designed to streamline municipal grievance redressal. It eliminates duplicate reporting through spatial clustering, automates administrative routing, and provides real-time status visibility to citizens and civic departments.

Distributed 3-Tier Microservices Architecture INTER-SERVICE DATA & EVENT FLOW
1. Citizen Reporting Frontend

Citizens submit geotagged civic grievances with real-time GPS pin-dropping, category classification, and image attachment. Instant duplicate checks alert users if an issue was already logged within 50 meters.

2. DBSCAN Clustering Microservice

Python microservice clusters incoming reports using Density-Based Spatial Clustering of Applications with Noise (DBSCAN) and great-circle Haversine distance, dynamically calculating centroid coordinates.

3. Municipal Redressal Backend & DB

Department officers triage grouped clusters, assign responsibilities to specialized civic departments (Roads, Sanitation, Electrical), update statuses, and broadcast live WebSocket updates to citizen maps.

The backend is structured as an event-driven RESTful API and WebSocket gateway built with Node.js and ES Modules. It coordinates database transactions, external microservice calls, geocoding, and client synchronization.

Key Code Symbols: app, server, io, initSocket(io), app.use('/api/issues', ...).

backend/src/db/pool.js Database Pool

Primary Function: Configures pg.Pool connection manager targeting PostgreSQL with SSL and idle timeouts. Exports safe helper methods query() and withTransaction() to ensure ACID compliance during multi-table writes.

Key Code Symbols: pool, query(text, params), withTransaction(callback).

Database Schema & Relational Structure (backend/src/db/schema.sql)

The schema contains 7 tables designed with UUID primary keys and strict referential integrity.

Table Name Primary Key Foreign Keys Purpose & Constraints
departments id (UUID) None Municipal agencies (BBMP Roads, BESCOM, BWSSB, Solid Waste Management).
users id (UUID) department_id → departments.id Citizens and municipal officers with bcrypt password hashes and role constraints.
issue_clusters id (UUID) assigned_department_id → departments.id DBSCAN-clustered geographic centroids (lat, lng), category, member count, and aggregate status.
issues id (UUID) user_id → users.id, cluster_id → issue_clusters.id Individual civic complaints with GPS coordinates, photos, ward names, and upvote counters.
status_logs id (UUID) issue_id → issues.id, changed_by → users.id Immutable audit trail recording all status transitions, officer notes, and timestamps.
upvotes (user_id, issue_id) user_id → users.id, issue_id → issues.id Composite primary key preventing duplicate voting on identical complaints.
refresh_tokens id (UUID) user_id → users.id Cryptographic SHA-256 hashed 7-day refresh tokens enabling secure silent session renewal.
⚡ Performance Indexes
B-Tree indexes are explicitly defined on issues(category), issues(status), issues(cluster_id), issues(user_id), issues(created_at), and status_logs(issue_id) to ensure sub-millisecond query performance over millions of civic records.

Backend Services & Route Controllers

Mechanics: Fetches all issues in a category reported within 30 days, POSTs them to the Python clustering service, and wraps results in a database transaction to create or update issue_clusters and link member issues. Emits cluster:updated over Socket.io.

Exported Functions: recluster(category), findNearbyCluster(lat, lng, category).

routes/analytics.js Router

Mechanics: Generates executive reports using PostgreSQL aggregate filters: totals by status, top 10 wards by complaint volume, average resolution time (in hours) calculated from status audit logs, and duplicate reduction rate %.

4 Python Spatial Clustering Microservice
PYTHON + SCIKIT-LEARN + DBSCAN

The clustering microservice (/clustering) is an autonomous Python service running on Flask. It solves the critical municipal challenge of citizen report duplication by applying mathematical spatial clustering over latitude and longitude coordinates.

clustering/app.py Flask API

Role: Hosts the microservice endpoints on port 5001. Provides GET /health for container orchestration checks and POST /cluster for executing batch spatial clustering.

Request Body: { category, issues: [{id, latitude, longitude, created_at}], eps_meters: 50, min_samples: 2, time_window_days: 30 }

Response Body: { status: "success", cluster_count: N, clusters: [{ centroid_lat, centroid_lng, member_count, issue_ids }] }

clustering/dbscan.py Algorithm Engine

Role: Pure mathematical engine implementing Density-Based Spatial Clustering of Applications with Noise (DBSCAN) using the spherical Haversine metric.

Key Steps:

  1. Temporal sliding window filtering (default 30 days).
  2. Coordinate conversion from degrees to radians.
  3. Epsilon conversion: \(\epsilon_{ ext{rad}} = rac{ ext{eps\_meters}}{R_{ ext{earth}}}\) with \(R = 6,371,000 ext{m}\).
  4. DBSCAN execution with metric='haversine' and algorithm='ball_tree'.
  5. Centroid calculation by averaging member latitudes and longitudes.
📐 Mathematical & Spatial Mechanics of DBSCAN

Standard Euclidean distance (\(\sqrt{\Delta x^2 + \Delta y^2}\)) creates severe geographic distortion when applied to spherical GPS coordinates. The clustering service converts degrees to radians and applies the Great-Circle Haversine Formula:

d = 2R \cdot rcsin\left(\sqrt{\sin^2\left( rac{\Delta \phi}{2} ight) + \cos(\phi_1)\cos(\phi_2)\sin^2\left( rac{\Delta \lambda}{2} ight)} ight)

With \(\epsilon = 50 ext{ meters}\) and \( ext{MinSamples} = 2\), two reports within 50 meters of each other coalesce into a single municipal cluster. Single reports (noise / \( ext{label} = -1\)) are returned as distinct 1-member clusters to guarantee zero lost reports.

Clustering Execution & Persistence Lifecycle END-TO-END ASYNCHRONOUS PIPELINE
STEP 1 Citizen Submits Issue: routes/issues.js receives geotagged report, persists it to issues table, and triggers recluster(category) asynchronously (non-blocking HTTP response).
STEP 2 Data Retrieval: clusterService.js queries all issues in the same category created within the last 30 days via fetchIssuesForClustering().
STEP 3 Microservice Call: Node.js POSTs coordinates array to http://localhost:5001/cluster. Python Flask passes data into run_dbscan_clustering().
STEP 4 Atomic DB Persistence: clusterService.js uses withTransaction() to upsert issue_clusters records and batch-update issues.cluster_id.
STEP 5 Real-Time Broadcast: Node emits cluster:updated via Socket.io to all connected municipal dashboards and citizen map views.

2. Authentication & JWT Rotation Workflow

The authentication subsystem uses short-lived JWT Access Tokens (15-minute lifespan) paired with cryptographically secure, SHA-256 hashed Refresh Tokens stored in HTTP-Only, SameSite cookies (7-day lifespan).

Token Issuance (Login) Security

Upon login, routes/auth.js issues a signed JWT containing sub (user.id), role, and department_id. A random 48-byte hex string is generated, hashed with SHA-256, and stored in refresh_tokens while the raw string is placed in a secure cookie.

Silent Token Refresh Security

When an access token expires, frontend Axios interceptor hits POST /api/auth/refresh. The backend verifies the cookie token hash against the database, confirms non-expiry, and returns a fresh 15-minute access token without requiring user re-authentication.
